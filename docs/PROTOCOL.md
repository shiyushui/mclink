# McLink 通信协议说明

版本 1.0.0 · 全部使用大端序（网络字节序）

服务端默认只占**一个端口号 7000**（TCP 与 UDP 命名空间独立，可以同号）：

| 通道 | 默认端口 | 传输层 | 用途 |
| --- | --- | --- | --- |
| 控制通道 + TCP 数据通道 | 7000 | TCP | 同一个端口，靠握手首条消息的类型分流 |
| UDP 隧道 | 7000 | UDP | 所有 UDP 映射复用这一条通道 |

> 想让控制与数据分开跑（例如按流量拆分、或做链路隔离），把配置里的 `data_port`
> 改成与 `control_port` 不同的端口即可，服务端会自动额外监听一个数据端口，
> 并在握手时把真实数据端口告知客户端。`data_port` 留空或等于 `control_port` 即为复用模式。

---

## 1. 控制通道

### 1.1 帧格式

```
+----------------+----------------------------+
| length (4B BE) | JSON payload (UTF-8, <=1MB)|
+----------------+----------------------------+
```

### 1.2 握手

客户端连上后**必须先发** `hello`：

```json
{ "t": "hello", "token": "<密钥>", "name": "<机器名>", "version": "1.0.0" }
```

服务端校验 `token`：

```json
{ "t": "hello_ok", "cid": "c1", "version": "1.0.0", "public_ip": "47.1.2.3",
  "allowed_ports": [[25565, 25570]], "control_port": 7000, "data_port": 7000, "udp_port": 7000, "ts": 1750000000 }
```

失败时返回 `{"t":"error","error":"密钥无效…"}` 并关闭连接。

### 1.3 客户端 → 服务端

| `t` | 字段 | 说明 |
| --- | --- | --- |
| `register` | `mapping: {mid, name, proto, remote_port}` | 请求在服务端开一个公网端口 |
| `unregister` | `mid` | 关闭该映射 |
| `ping` | `ts` | 心跳，服务端回 `pong`（客户端据此算延迟） |
| `get_info` | — | 请求服务端信息 |
| `bye` | — | 优雅退出 |

`register` 的校验顺序：`mid` 非空 → `proto ∈ {tcp, udp}` → `1 ≤ remote_port ≤ 65535`
→ 不与 McLink 自身端口冲突 → 在 `allowed_ports` 白名单内 → 未被其他客户端占用
→ 尝试 `bind` 成功。任一步失败返回 `register_err`。

### 1.4 服务端 → 客户端

| `t` | 字段 | 说明 |
| --- | --- | --- |
| `register_ok` | `mid, tunnel_id, remote_port` | 注册成功，`tunnel_id` 用于 UDP 隧道寻址 |
| `register_err` | `mid, error` | 注册失败原因（中文，可直接给用户看） |
| `unregister_ok` | `mid` | — |
| `dial` | `tok, mid, proto` | **有玩家连上来了，请立刻回连数据通道** |
| `stats` | `data: {mid: {...}}` | 每 2 秒推送一次流量/连接数统计 |
| `pong` | `ts` | 心跳回应 |
| `info` | `info: {...}` | 服务端信息 |
| `bye` | `reason` | 服务端要关闭了 |

`stats` 里每一项：

```json
{ "mid":"m1", "name":"MC", "proto":"tcp", "remote_port":25565, "tunnel_id":1,
  "rx":1024, "tx":2048, "active":1, "total":12, "status":"active", "error":null }
```

方向定义（以**公网侧**为准）：`rx` = 玩家 → 家里游戏（入站），`tx` = 家里游戏 → 玩家（出站）。

## 2. TCP 数据通道（默认复用控制端口 7000）

控制连接和数据连接**使用完全相同的帧格式**，所以可以在同一个端口上共存，
服务端读第一条消息后按 `t` 字段分流：

| 首条消息 | 分流去向 |
| --- | --- |
| `{"t":"hello", ...}` | 控制会话（鉴权 → 注册映射 → 心跳循环） |
| `{"t":"mux", ...}` | 数据连接（配对到挂起的公网连接） |

```
 玩家 ──▶ 服务端:25565 收到连接
          │ 1. 生成一次性 tok = 16字节随机数的 hex
          │ 2. 控制通道下发 {"t":"dial","tok":...,"mid":"m1"}
          ▼
 客户端 ──▶ 2'. 连 服务端:7000，发送帧 {"t":"mux","tok":"<同一个 tok>","mid":"m1"}
          ▼
 服务端：在挂起表里用 tok 找到对应的公网连接，配对成功
          ▼
 之后这条连接上就是**裸字节流**，不再有任何分帧，双向 pipe
```

`hello_ok` 里会带上 `data_port`，客户端以它为准（这样服务端改端口不用改客户端配置）。

- `dial` 后 8 秒内（`dial_timeout_s` 可配）没有匹配的 mux 连接，服务端关闭公网连接
  并把该映射标记为 `error`（客户端会提示"回连超时"）。
- 客户端收到 `dial` 后，先连服务端数据通道，再连本地游戏端口 `local_host:local_port`；
  本地连不上则在 UI 上报"本地端口不可用"。
- 单条连接空闲超过 `idle_timeout_s`（默认 300 秒）自动断开，防止连接泄漏。
- 每个映射的并发连接数上限 `max_conns_per_mapping`（默认 256）。

采用"服务端下命令、客户端回连"而不是长连接池，是因为这样**每条玩家连接都是独立的
TCP 连接**，不会因为某条游戏连接阻塞而互相影响，实现也简单可靠。

## 3. UDP 隧道

所有 UDP 映射共用服务端的 7000/udp 端口。包头固定 6 字节 + 地址 6/18 字节。

### 3.1 注册 / 保活（客户端 → 服务端）

```
 0        1        2        3        4        5        6
+--------+--------+--------+--------+--------+--------+---------+
|  'M'   |  'L'   | 0x01   | TOKLEN |   TUNNEL_ID     |  TOKEN  |
+--------+--------+--------+--------+--------+--------+---------+
   MAGIC(2B)        TYPE    1B        2B BE            TOKLEN 字节
```

客户端每 20 秒重发一次（同时起到保持 NAT 映射不失效的作用）。
服务端收到后记录该 socket 的源地址作为回程地址，并回一个 `PONG`：

```
MAGIC(2) | 0x03 | 0x00 | TUNNEL_ID(2)
```

### 3.2 数据（双向同格式）

```
+--------+--------+--------+--------+--------+---------+--------+---------+
|  'M'   |  'L'   | 0x02   | FAMILY |  TUNNEL_ID      |  ADDR  |  PORT   | PAYLOAD |
+--------+--------+--------+--------+--------+---------+--------+---------+
                 TYPE=2    4 或 6     2B BE           4/16B    2B BE
```

| 方向 | `ADDR:PORT` 的含义 |
| --- | --- |
| 服务端 → 客户端 | 玩家的公网地址（客户端据此决定回包送给谁） |
| 客户端 → 服务端 | 同上，服务端据此把包发给对应玩家 |

包头开销：IPv4 场景 12 字节，IPv6 场景 24 字节。

### 3.3 客户端本地会话模型

UDP 是无连接的，为了让游戏的回包能对上是哪个玩家，
客户端**为每个玩家建立一个独立的本地 UDP socket**（`connect()` 到 `local_host:local_port`）：

```
玩家 A ──▶ 隧道 ──▶ 客户端 socket#1 ──▶ 本地游戏 19132
玩家 B ──▶ 隧道 ──▶ 客户端 socket#2 ──▶ 本地游戏 19132
                        │
        socket#1 收到回包 ⇒ 一定回给玩家 A
```

- 每个映射最多保留 64 个玩家会话（`MAX_UDP_SESSIONS`）。
- 会话空闲 90 秒回收（`UDP_SESSION_IDLE_S`）。
- socket 建立完成前的包会先缓存（`pending`），保证 **首包不丢**——
  基岩版的 `Unconnected Ping` 就是首包，丢了会显示"无法连接"。

---

## 4. 断线重连

客户端控制通道断开后按 `1 → 2 → 4 → 8 → 15 → 30`（上限 30 秒）退避重连，
重连成功后**所有映射重新注册**（服务端的会话状态是内存态，不持久化）。

服务端 30 秒清一次超过 150 秒没有保活的 UDP 隧道登记，避免向失效的 NAT 地址发包。

---

## 5. 鉴权与安全边界

- 控制通道必须提供正确密钥，否则立刻断开；密钥比较对 `token` 字段做常量时间比较
  （Web 控制台口令用 `secrets.compare_digest`）。
- TCP 数据通道没有独立密钥，靠**一次性随机 `tok`**（16 字节）保证只有收到 `dial`
  指令的那个客户端能配对成功。
- UDP 隧道的注册包里带密钥，服务端校验通过才登记回程地址。
- 客户端无法申请白名单以外的公网端口，也无法抢注其他客户端已占用的端口。
- 服务端不转发任何"未注册端口"的流量：没有映射 = 没有监听。
